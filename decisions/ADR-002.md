# ADR-002: Use Request-Response Communication for v0.1

## Problem

The system needs the App/Web to communicate with the Backend for actions such as
submitting requests, viewing requests, and checking their status.

The current requirements do not require real-time communication.
Status updates only need to become visible eventually, and real-time chat is not
part of the system.

Because of this, we need to decide whether to use normal request-response
communication or a real-time connection such as WebSockets.

## Options

### Option 1: Request-response communication

The App/Web sends a request to the Backend when it needs information or wants to
perform an action.

Advantages:
- Simple to implement and understand.
- Fits the current requirements.
- Does not require a permanent connection between the client and Backend.
- Polling can be used when status updates need to refresh automatically.

Disadvantages:
- Updates are not pushed immediately to the user.
- Polling creates repeated requests to the Backend.

### Option 2: WebSockets

Keep a persistent connection between the App/Web and the Backend so updates can
be sent immediately.

Advantages:
- Updates can appear in real time.
- Useful for features such as live chat or live notifications.

Disadvantages:
- Adds more complexity.
- Requires persistent connections.
- Real-time updates are not currently required by the system.

## Decision

For v0.1, the App/Web will communicate with the Backend using request-response
communication.

WebSockets will not be added because there is currently no requirement for
real-time communication.

We can use polling for status information to refresh automatically.

## Consequences

### Positive
- Communication stays simple.
- The solution matches the current requirements.
- There is less complexity to manage.

### Negative
- Status changes will not automatically appear instantly.
- If the number of users grows a lot, frequent polling could increase Backend load.

### Future Consideration

If future requirements include real-time notifications, live updates, or chat, WebSockets can be considered.

Also, if polling creates too much load on the Backend as the number of users grows, the communication approach can be reviewed and a more suitable real-time method can be considered.

So, we need to monitor the system load and review future requirements before deciding whether a different communication approach is needed.
