# ADR-001: Use a Centralized Architecture for v0.1

## Problem

The system needs to support employees submitting and tracking internal requests,
while department staff handle requests for their departments.

The expected number of users, requests per day, and required throughput are
currently unknown.

Because the expected load is not known, it is unclear whether a distributed
architecture such as microservices or message queues is necessary.

## Options

### Option 1: Simple centralized architecture

Use one App/Web application communicating with one Backend, which communicates
with persistent storage.

Advantages:
- Simple to design and maintain.
- Satisfies the currently known requirements.
- Fewer components and dependencies.
- Easier to change while requirements are still evolving.

### Option 2: Distributed architecture

Introduce components such as microservices, message queues, Redis, (or other external dependecies) from the beginning.

Advantages:
- Can support more complex scaling requirements.
- Allows components to scale independently.

Disadvantages:
- Adds complexity.
- Adds operational overhead.
- Current requirements do not justify it.

## Decision

Use a simple centralized architecture for v0.1.

The App/Web communicates directly with the Backend, and the Backend communicates
with persistent storage.

Additional components will only be introduced when requirements such as load,
scalability, or reliability justify them.

## Consequences

### Positive
- The initial architecture remains simple.
- Development and maintenance are easier.
- There are fewer components that can fail.
- The architecture satisfies the currently known requirements.

### Negative
- Components cannot scale independently as easily as in a distributed architecture.
- The architecture may need to evolve if future load becomes significantly larger.

### Future consideration ( very important )
When expected user load, request volume, or scalability requirements become
known, the architecture should be reviewed.
