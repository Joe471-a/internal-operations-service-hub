# ADR-004: Deploy on Render with PostgreSQL and Two Services

## Problem

Until Week 4 the hub only ran on a developer's laptop, with its data in a SQLite
file (`backend/prisma/hub.db`). The final release has to run on a remote target that
does not depend on anyone's laptop, keep its data across restarts, and cost nothing.

The chosen host, Render (free plan), gives each web service a disk that is **wiped on
every restart and redeploy**, and free services restart often (every deploy, and
after about 15 minutes without traffic). A SQLite file on that disk would lose every
user and request each time.

Two decisions were needed:

1. which database engine to use now that the app is deployed, and
2. how to host the frontend and the backend.

ADR-003 (use a relational database) still holds - both options below are relational.
This decision is about the engine and the hosting, not the data model.

## Options - database engine

### Option 1: Keep SQLite

Advantages:
- No change to the code or the setup.
- Nothing extra to run locally.

Disadvantages:
- The data would be lost on every restart of the free Render service.
- Keeping it would need a paid persistent disk, and hosting is required to be free.

### Option 2: PostgreSQL

Advantages:
- Runs as its own service (Render's managed PostgreSQL), so the data survives
  restarts and redeploys of the backend.
- Free on Render, and the most widely used open-source relational database.
- Prisma supports it fully: the schema, models and queries stay the same; only the
  provider changes and the address comes from `DATABASE_URL`.

Disadvantages:
- Local development and tests now need a PostgreSQL server too.
- Render's free PostgreSQL is meant for development, not long-term production data.

### Option 3: MySQL or another relational engine

Advantages:
- Also relational and supported by Prisma.

Disadvantages:
- Not offered as a managed free service on Render; it would need another provider.

## Options - hosting

### Option A: One service serving both the frontend and the API

Advantages:
- One address, one deploy, no CORS setting and no API address to configure.

Disadvantages:
- On the free plan, the whole site - page included - sleeps with the backend, so a
  visitor sees nothing for up to 50 seconds.
- Every frontend change restarts the API, and the other way round.

### Option B: Two services - a static site for the frontend and a web service for the API

Advantages:
- The frontend is plain files served instantly by a static site that never sleeps.
- The two deploy independently.
- It mirrors the App/Web and Backend split in the architecture (ADR-001).

Disadvantages:
- The frontend needs the API's address (`VITE_API_URL`), and the API must allow the
  frontend's address (`CORS_ORIGIN`).

## Decision

**PostgreSQL 16 on Render** replaces SQLite, and the hub is deployed as **two
services**: `hub-frontend` (static site) and `hub-backend` (web service), with the
database as a third, managed service. All three are on Render's free plan, in the
same region.

- The database address comes from `DATABASE_URL`, so the same code runs against
  Render's PostgreSQL live, a PostgreSQL in Docker locally (`docker-compose.yml`,
  same version 16), and a throwaway PostgreSQL in CI.
- Tests use their own database (`hub_test`) and never touch the app's data.
- The schema is kept in sync at startup (`prisma db push` in the start command), so a
  schema change ships with the code in one step while the schema may still change.

## Consequences

### Positive
- Data survives restarts and redeploys.
- Development, CI and production all run the same database engine and version, so a
  bug that only appears on PostgreSQL is caught before release - moving to it surfaced
  one in the tests (history rows assumed to come back in insertion order, which
  SQLite happened to do and PostgreSQL does not promise).
- The login page appears instantly even while the free backend is waking up.
- The frontend and the backend can be deployed and rolled back separately.

### Negative
- A local PostgreSQL is now needed for development and tests (one command with Docker).
- Two extra settings to keep correct: `VITE_API_URL` and `CORS_ORIGIN`.
- On the free plan the backend sleeps after about 15 minutes without traffic, and the
  first request after that takes 30-50 seconds. The UptimeRobot health check every 5
  minutes keeps it awake, so in practice it only sleeps if that monitor is stopped.
- Syncing the schema at startup can create a missing database - a wrong database name
  starts the app on an empty database instead of failing (see
  `docs/week5-failure-drills.md`, drill 2b). This is caught by the smoke test.

### Future Consideration

When the schema is stable, schema changes should become a deliberate release step
(versioned migrations run before the deploy) instead of happening at startup. For
real production data, the database would move to a paid plan with backups, and a
paid backend instance would remove the sleeping.
